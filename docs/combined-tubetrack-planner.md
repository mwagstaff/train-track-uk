# TubeTrack combined planner v5

`POST /api/v5/journey-planner/search-jobs` accepts map `origin` and `destination`
IDs, `time`, `timeType` (`departAfter`/`arriveBy`) and `accessibility`
(`none`/`platform`/`train`). It returns the existing job lifecycle; GET/DELETE use
`/api/v5/journey-planner/search-jobs/:id`. There are no v3-compatible cursors or
cross-version detail IDs in this contract. Refresh submits a new search.

V5 is isolated from v3's RAPTOR-only policy. A `combinedSearch` worker operation
uses the existing asynchronous, independently validated router with live rail
overlays and time-dependent TfL connections. Dates/datasets are shared with the
worker's existing engine; augmented graphs and live contexts are separate.
The gateway explicitly forwards the new namespace. Old v1–v4 routes retain their
contracts and default policies.

Scope is the 676 stations in `resources/combined-stations.json`, generated by
TubeTrack's `build-combined-stations.js`. Both endpoints and changes are on-map;
trains may pass outside the map. Bounds are five changes, six hours travel and
a six-hour search window. Ordinary buses, ferries and generic metro links are
excluded; official `replacementBus` timetable services are included.

Synthetic graph links supply only optimistic search bounds. They never become
fallback journey times. TfL unavailability can retain genuine ALF allowances but
cannot invent access from a Tube-only endpoint. Equal reviewed TfL access points
use the railway station allowance and explicit walking directions. Step-free
requests reach TfL; National Rail/bus accessibility is labelled unverified.

Time-order traversal spends the bounded TfL budget on early useful stations first.
V5 has one executing job, four admitted jobs, per-client/network limits and a
60-second execution budget. It shares existing worker capacity: versioning protects
contracts, not CPU/RAM isolation. Monitor old-client latency under rollout load.

Deployment order: TubeTrack API (including v2 journey-transfers), then planner
worker/service and gateway, then iOS. The performance-only update needs no gateway
or iOS change. See [performance harness](combined-planner-performance.md).
No timetable migration is needed. Ship matching catalogues. See TubeTrack's
`api/tube-track-api/docs/combined-journeys.md` for the app-facing response and
freshness rules. Tests: `test/planner-combined.test.js` and
`test/planner-combined-http.test.js`, plus existing router, TfL, live and job suites.
